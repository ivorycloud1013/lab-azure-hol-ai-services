# Foundry Harness — 틀린 답을 알아보는 하네스를 짓는 랩

모델을 부르는 코드는 다들 한 번쯤 써봤습니다. 그 코드가 **에이전트**가 되려면 주위에
무엇이 더 있어야 하는가 — 이 랩은 그걸 한 층씩 직접 지으면서 답합니다.

## 이 랩이 다루는 실패

에이전트를 처음 만들면 이 순서로 실패합니다.

| | 무엇이 문제인가 | 어떻게 보이는가 |
|---|---|---|
| 1 | 자료가 없다 | 아는 척하며 지어낸다 |
| 2 | 자료는 있는데 **이미 대체된 문서에서** 집어 온다 | 근거까지 달고 자신 있게 틀린다 |
| 3 | 틀린 걸 아무도 안 본다 | 그대로 사용자에게 나간다 |

1번은 툴을 붙이면 끝납니다. 데모가 여기서 멈추는 이유이기도 합니다.
**이 랩의 본론은 2번과 3번입니다.**

코퍼스에는 같은 보고서의 **edition 이 둘** 들어 있습니다. 하나는 이미 대체된 구판이고, 하나는
수정본입니다. 둘은 줄 번호까지 같고 수치 몇 개만 다릅니다. 파일이 인덱스에 두 번 들어간
것뿐이고, **문서는 자기가 대체된 줄 모릅니다.** 실무의 코퍼스가 꼭 이렇습니다.

그래서 검색은 두 edition 을 다 물어오고, 모델은 어느 쪽이 살아 있는지 판단할 근거가 없습니다.
없는 정보라서 더 좋은 모델을 써도 달라지지 않습니다. 실제로 두 가지로 실패합니다 —
하나를 골라 확신하고 틀리거나(`자신 있게 틀림`), 충돌을 알아채고도 고르지 못해 양쪽을
나란히 적습니다(`판단 회피`). 뒤쪽도 답이 아닙니다. 고르는 일을 사용자에게 떠넘긴 것이고,
사용자에게는 고를 근거가 더 없습니다.

질문 세트(`golden.py`)는 **답이 어느 edition 을 봤느냐에 따라 갈리는 질문**으로 앞의 셋을 채우고,
뒤의 셋은 두 edition 에서 값이 같은 대조군으로 두었습니다.

## 진행 순서

| 단계 | 파일 | 짓는 것 | 결과 |
|---|---|---|---|
| 0 | `step0_baseline.py` | (아무것도 없음) | 문서가 없으니 **지어낸다** |
| 1 | `step1_tools.py` | 스키마 · 디스패처 · 루프 · 실패 처리 | 찾아온다. 그런데 **대체된 문서에서 찾아온다** |
| 2 | `step2_verify.py` | 근거 검증 · edition 검사 · 반려 · 재시도 | 하네스가 **오답을 알아채고 다시 찾는다** |

시나리오는 **step 2 에서 닫힙니다.** step 1 이 틀리고, step 2 가 잡고, 모델이 고쳐 옵니다.

**각 단계는 자기 대조군을 들고 있습니다.** 대조군 없이 한 번만 돌리면 그 단계는
아무것도 주장하지 않습니다.

```bash
cd python
export AZURE_AI_PROJECT_ENDPOINT="<foundry-project-endpoint>"

# 0 — 하네스 없이. 지어낸 인용이 어떻게 생겼는지 본다
python harness/step0_baseline.py --endpoint "$AZURE_AI_PROJECT_ENDPOINT" --questions 3

# 1 — 툴을 준다. 답을 찾아오는데, '자신 있게 틀림' 이 몇 개인지 본다
python harness/step1_tools.py --endpoint "$AZURE_AI_PROJECT_ENDPOINT" --questions 3 --show-tools
python harness/step1_tools.py --endpoint "$AZURE_AI_PROJECT_ENDPOINT" --questions 3 --broken-tools

# 2 — 검증을 붙인다. 첫 답과 마지막 답이 어떻게 달라지는지 본다
python harness/step2_verify.py --endpoint "$AZURE_AI_PROJECT_ENDPOINT" --questions 3
python harness/step2_verify.py --endpoint "$AZURE_AI_PROJECT_ENDPOINT" --questions 3 --no-verify
```

**PowerShell** 은 줄 이음만 `` ` `` 로 바꾸면 동일합니다.

## 검증은 정답을 모른다

step 2 의 규칙 하나만 기억하면 됩니다.

> **하네스는 정답을 모릅니다.** 알았다면 모델을 부를 이유가 없습니다.

그래서 검증은 "이 답이 맞는가" 를 묻지 않습니다. 대신 이렇게 묻습니다 —

> **"이 답이 근거로 댄 자리가, 이 답을 실제로 뒷받침하는가?"**

정답 없이 확인할 수 있고, 오답의 상당수가 여기서 걸립니다.

여기에 이 코퍼스가 요구하는 겹이 하나 더 붙습니다. 하네스는 어느 문서가 살아 있는지를
압니다. 그게 정답을 아는 것과 어떻게 다른지가 중요합니다 —

| | |
|---|---|
| 하네스가 **아는** 것 | 어느 문서가 현행인가 (문서 관리 메타데이터) |
| 하네스가 **모르는** 것 | 서울 청약 경쟁률이 얼마인가 (정답) |

이 지식은 문서 안에서는 얻을 수 없습니다. 구판은 자기가 대체된 줄 모르니까요. 그래서
`golden.py` 의 `EDITIONS` 에 적혀 있고, **step 2 부터만 읽습니다.** step 1 이 그 표를
읽지 않는다는 것이 "step 1 에는 edition 개념이 없다" 의 코드상 의미입니다.

검증은 세 겹이고, **싼 것이 먼저 거릅니다.**

| 겹 | 무엇을 보나 | 비용 |
|---|---|---|
| 결정론 · 인용 | 인용이 있나 · 인용한 줄에 그 수치가 정말 있나 | 모델 호출 0번 |
| 결정론 · edition | 대체된 문서에만 있는 수치를 말하고 있나 | 모델 호출 0번 |
| 근거 판정 | 그 줄이 질문이 물은 대상의 값이라고 확정해 주나 | 모델 호출 1번 |

순서를 뒤집으면 지어낸 인용 하나를 잡는 데 판정 비용을 냅니다. 그리고 판정자에게는
**정답을 주지 않습니다.** 답안지를 쥔 판정자는 하네스가 아니라 채점 기계이고, 실전에는
그런 게 없습니다.

edition 검사가 묻는 것이 **"폐기된 문서를 봤나" 가 아니라 "그 수치가 살아 있는 edition 에도 있나"**
라는 점을 눈여겨보세요. 앞으로 물으면 두 edition 에서 값이 똑같은 수치까지 되돌리게 되고,
대조군 세 문항이 전부 거기 걸립니다. 답은 멀쩡한데 값을 치르고 뭉개는 것 — 다음 절의
**헛수고** 칸이 그래서 오릅니다. 반려할 때도 **현행 문서 이름만 알려주고 정정된 수치는
말하지 않습니다.** 말하는 순간 하네스가 답을 불러주는 것이 됩니다.

반려할 때 사유와 다음 할 일을 함께 돌려주는 것도 규칙입니다. "틀렸다" 만 돌려주는 검증은
재시도를 **반복**으로 만들고, 무엇이 왜 부족한지 돌려주는 검증은 재시도를 **조사**로
만듭니다. 이 차이가 step 2 의 전부입니다.

## 검증은 공짜가 아니다

리포트의 **헛수고** 칸을 꼭 보세요. 맞는 답을 반려한 횟수입니다.

|  | 하네스 통과 | 하네스 반려 |
|---|---|---|
| **정답** | 정상 | **헛수고** — 값을 치르고 답을 뭉갠다 |
| **오답** | **위험** — 자신 있게 틀린 답이 나간다 | 잡아냈다 |

step 1 은 왼쪽 아래 칸이 그대로 나가는 상태입니다. step 2 는 그걸 오른쪽 아래로 옮기고,
재시도로 왼쪽 위까지 밀어 올립니다. 그 과정에서 오른쪽 위 칸이 같이 커집니다.
**검증을 조이면 hit 은 그대로면서 헛수고만 오르는 변경이 아주 흔합니다.** hit 만 보는
리포트는 그걸 "변화 없음" 이라고 말합니다. 두 칸을 같이 보세요.

## 파일 구성

```
harness/
  harness_tools.py     grep · sed — 능력. 전 단계 공통이고 절대 바뀌지 않는다
  harness_verify.py    검증 레이어. 결정론 검사(인용 · edition) + 근거 판정
  harness_metrics.py   공용 계측. ToolResult · 지표 계산 · 리포트 형식
  golden.py            질문 6개와 edition 목록. 정답은 수정본 값, lure 는 구판 값
  harness_cli.py       인자와 클라이언트 배선. 하네스가 아니라 보일러플레이트
  harness_loop.py      step 1 이 완성한 루프를 뽑아둔 것. step 0 · 2 가 가져다 쓴다
  step0_baseline.py · step1_tools.py · step2_verify.py

assets/tools/harness/  코퍼스. 같은 보고서의 두 edition
  KB-2510-4471.md      대체된 구판
  KB-2510-8092.md      현행 수정본 — 수치 3개가 다르고, 줄 번호는 같다
```

파일 이름에 edition 정보가 없는 것은 의도입니다. `_수정본` 이나 `_v2` 로 두면 모델이 이름만 보고
최신을 골라 버려서, 이 랩이 보여주려는 실패가 일어나지 않습니다. 문서 **본문에도** edition 표시가
없습니다.

`harness_tools.py` 와 나머지의 경계가 이 랩의 설계입니다. **능력은 고정, 하네스는 여러분이
짓는 것.** 검색 능력이 한 글자도 안 바뀌므로, 숫자가 움직였다면 그건 하네스가 한 일입니다.
지시문도 step 0 부터 2 까지 같은 문장을 씁니다 — 그래야 hit 이 오른 것을 문구 덕으로
돌릴 수 없습니다.

## 지표는 어떻게 계산되나

| 지표 | 계산 |
|---|---|
| `hit` | 정답 문자열이 전부 있고 **구판 값은 없는가.** LLM 0콜 |
| `자신 있게 틀림` | 대체된 문서를 근거로 달고 낸 오답의 수 (step 1) |
| `판단 회피` | 두 edition 의 값을 나란히 적고 고르지 않은 답의 수 (step 1) |
| `첫 답 오답` | 검증이 없었다면 그대로 나갔을 오답의 수 |
| `하네스 반려` | 검증이 되돌려 보낸 횟수. 그중 모델 없이 잡은 것을 따로 센다 |
| `폐기 edition 반려` | 그중 edition 검사가 잡은 횟수. LLM 0콜 |
| `재시도로 교정` | 첫 답이 틀렸다가 마지막에 맞은 질문 수 |
| `헛수고` | **맞는 답**을 반려한 횟수 |
| `tool error rate` | 디스패처가 거부한 호출 / 전체 툴 호출 |

**전부 심판 없이 나옵니다.** 채점기도, 추가 패키지도 필요 없습니다. 이 랩이 주장하는 것은
전부 문자열 대조와 산술이라, 몇 번을 돌려도 같은 숫자가 나옵니다.

## 알아둘 것

- **`--questions 3` 아래로 줄이지 마세요.** 앞의 세 문항이 함정 문항이고, 그 아래로
  줄이면 이 랩이 보여주려는 실패가 표본에서 빠집니다.
- 문항이 6개뿐이라 **작은 차이는 운입니다.** 두 설정을 비교할 때 한 문항 차이로
  결론 내지 마세요.
- step 2 는 질문마다 최대 3번 시도하고 시도마다 판정 호출이 하나 붙습니다.
  **step 1 보다 몇 배 비쌉니다.** 그게 이 레이어의 청구서이고, 리포트에 그대로 잡힙니다.
- 이 랩은 Foundry 에 agent 도 vector store 도 만들지 않습니다. 모델 호출 말고는 아무것도
  남기지 않습니다.
